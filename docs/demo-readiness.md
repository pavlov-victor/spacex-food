## Конкретные блокеры логики

1. `frontend/convex/lib/dify.ts:downloadGeneratedImage` допускает только x.ai. У fal URL на fal.media, поэтому генерация закончится потерей картинки при сохранении. Добавить проверенные домены fal с сохранением проверок HTTPS, MIME и размера; проверить реальное скачивание в Convex.
2. `jobs.finishCard` сохраняет JSON в cards и cardId в products, но не применяет описание/перевод. `storefront.publish` читает product.name/description, а не карточку. Нужен явный шаг принятия отредактированного черновика с записью английского имени/описания и сохранением исходного имени; автоматически принимать AI-состав не надо.
3. Publish копирует snapshot: новая генерация сама публичное меню не обновляет. Показать необходимость повторной публикации либо встроить её в явную кнопку обновления.
4. Backend по умолчанию отправляет target_languages=sr,en,ru, текущий product DSL фиксирован на en. Убрать устаревший параметр/ожидания UI.
5. Последний проверенный Dify API-прогон вернул workflow_version=0.0.6. Версия 0.0.8 проверена локальными code nodes и прямым fal-вызовом. Импортировать/опубликовать 0.0.8-release.yml и проверить именно через Dify, затем через Convex.
6. Импорт меню не гарантирует состав: в проверенных данных description=null. Показывать отсутствие состава и дополнять его на шаге обогащения/подтверждения, не обещать распознанные ингредиенты для каждой позиции.

## Render

Рекомендуемый вариант на время хакатона: один Render Static Site обслуживает CRM и `/menu/:slug`; Convex Cloud хранит данные, файлы, авторизацию и фоновые задачи; Dify Cloud выполняет workflow, fal создаёт картинки. Это размещение сайта на Render, а не перенос всех сервисов в Render. Self-hosted Dify/Convex — отдельный объём работ.

`render.yaml` уже задаёт rootDir=frontend, `npm ci && npm run build`, dist и rewrite /* → /index.html. Настроить VITE_CONVEX_URL на выбранный облачный deployment. Ключи Dify и Auth должны быть на том же Convex deployment, FAL_KEY/EXA_API_KEY и текстовый provider — в Dify. API-ключи не передавать через VITE_.

Для короткого контролируемого демо можно использовать уже подготовленный dev Convex (по docs/deployment.md); не переключать frontend на пустой production deployment. Для постоянной среды отдельно настроить production и его secrets. Frontend и Convex деплоятся отдельно при текущем Blueprint. Ветка Render должна содержать актуальные изменения. Публичную доступность и refresh `/menu/:slug` проверить на реальном URL.

Источники: https://render.com/docs/static-sites , https://docs.convex.dev/production/hosting/custom .

## Минимальный порядок завершения

1. Исправить сохранение fal и принятие черновика; проверить опубликованный Dify DSL.
2. Подключить CRM к готовым hooks: регистрация → импорт → список → редактор → Generate/Regenerate → Publish.
3. Добавить QR и ссылку; состав/иконки подтверждаются отдельно от AI-предположений.
4. Передать друзьям отдельные аккаунты; для открытого самостоятельного доступа добавить небольшой лимит генераций на организацию. Сейчас activeJobId предотвращает повтор по одному блюду, но не ограничивает общий расход.
5. Deploy на Render, затем один реальный проход в чистом браузере и открытие QR с другого телефона без логина. Проверить повторный вход, сохранение после refresh, ошибку генерации и вторую организацию.

Критерий готовности: новый пользователь без Dify UI/терминала создаёт ресторан, импортирует фото меню, обогащает одну позицию, перегенерирует с реальным фото, принимает результат и публикует меню, доступное по QR с другого устройства.

Отложить: биллинг, аналитику, массовую генерацию всех блюд, дополнительные языки, сложные роли и self-hosting. UI принадлежит участнику дизайна; hooks/Convex — участнику логики согласно docs/team-development.md.
