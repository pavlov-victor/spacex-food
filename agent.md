# Контекст проекта

Обновлено: 2026-09-12. Этот файл фиксирует требования владельца проекта и двух предоставленных схем. Предложения по реализации отмечены отдельно.

## Продукт и бизнес

- B2B-приложение для сербских кафан и ресторанов, создаваемое в рамках SpaceX Hackathon Belgrade.
- Цифровизация бумажного меню: ресторан загружает фото меню и/или текстовое описание, получает структурированное цифровое меню; посетитель открывает его по QR-коду.
- Ценность: удобство для туристов, автоматизация работы с меню, автоматический перевод.
- Планируемая бизнес-модель — подписка. Оплата и тарифы пока не реализуются.
- На разработку осталось несколько часов: приоритет — работающий демонстрационный сценарий.

## Текущий scope и стек

- Задача текущей сессии — фронтенд: React-приложение CRM для ресторана. Владелец будет присылать референсы и продуктовые решения для последовательной реализации интерфейсов.
- Для размещения витрины цифрового меню используем Render из стека хакатона. Конкретный дизайн и реализация витрины ещё не согласованы.
- Runtime и оркестрация LLM workflow находятся в Dify.
- Grok API / x.ai — текстовые и мультимодальные задачи; x.ai Image / Imagine — генерация изображений.
- Не переносить оркестрацию в собственный бекенд без изменения требований владельцем.
- Примерный стек хакатона: https://hackathon.cursorserbia.com/stack.
- Страница перечисляет Grok Bot/Cursor, Firecrawl, Exa, Wonder, Daytona, Convex, Wispr Flow, Fal.ai, x.ai и Render. Это доступные варианты, а не требование интегрировать все сервисы. Для изображений выбор владельца — x.ai.
- В `.env` имеются переменные `XAI_API_KEY`, `EXA_API_KEY`, `FIRECRAWL_API_KEY`, `SPACEX_MCP`. Наличие переменной не означает, что ключ проверен.
- Не копировать значения ключей и полный MCP URL в документацию, workflow, логи или клиентский код. MCP URL содержит доступ к приложению.

## Требования из схем

### Загрузка и работа с меню

- Вход: фотография меню, текстовое описание и промпт/инструкции.
- Выход: список продуктов/блюд и QR-код для доступа к цифровому меню.
- Владелец может редактировать и удалять блюда.
- Для блюда создаются текстовое описание и LLM-переводы.
- Для блюда генерируется изображение; дополнительные входы для него — фото стола и промпт, задающий желаемый результат.
- Дополнительное обогащение: интересные факты о блюде через API поиска.
- Классификация: веганское, аллергены, низкокалорийное, острое, детское меню, takeaway/упаковка.

### Интерфейсы

- CRM / веб-приложение ресторана: создание организации, настройки, управление меню и генерация изображений.
- Клиентское приложение: мобильное веб-приложение с удобным UX и автоматическим переводом.
- QR ведёт на опубликованную страницу меню. Постоянный URL, хранение и публикация требуют следующего этапа с бекендом/фронтендом.

## Предложение по реализации Dify MVP

Это проект решения, а не уже созданный или проверенный workflow.

1. Start: фото меню и/или текст, инструкции ресторана, языки перевода; опционально фото стола, стиль изображения и URL опубликованного меню.
2. Grok с поддержкой изображений: распознать названия, разделы, описания, цены, валюту и размеры порций. Сохранить исходный текст; не додумывать неразборчивые значения.
3. Проверка структуры: привести результат к JSON; отмечать пропущенные и сомнительные поля для редактирования рестораном.
4. Обработка блюд: описания, переводы, классификация и промпт изображения. Точный набор языков ещё не согласован; для демо предлагаются сербский, английский и русский.
5. x.ai Image: сгенерировать иллюстрацию блюда, по возможности с референсом стола через поддерживаемый API. Конкретную модель и поддержку референса проверить перед реализацией.
6. Опционально Exa/Firecrawl: найти факты с URL источников. Это дополнительная возможность, которая не должна блокировать основной сценарий.
7. End: вернуть структурированное меню, переводы, статусы обработки и ссылки на изображения. Возвращать URL меню только если он реально предоставлен/создан; QR кодировать обычной библиотекой или сервисом, а не генеративной моделью.

### Предлагаемый контракт результата

- Меню: `schema_version`, `source_language`, `currency`, `items`, `warnings`.
- Блюдо: `id`, `category`, `original_name`, `original_description`, `price`, `portion`, `translations`, `classification`, `image_url`, `fun_facts`, `needs_review`.
- Переводы: названия и описания по коду языка, исходные названия сохраняются.
- Классификация: значения `true` / `false` / `unknown`; для аллергенов список и статус подтверждения.
- Не утверждать отсутствие аллергенов по фото или названию блюда. Не выдумывать ингредиенты, калории, доступность упаковки или пригодность для детей. Неподтверждённые сведения требуют проверки рестораном.
- Генерируемое изображение — иллюстрация, его происхождение должно быть доступно будущему интерфейсу.
- Ошибка изображения или поиска не должна терять успешно распознанное меню.
- На демо ограничить обогащение несколькими блюдами, чтобы контролировать время и стоимость. Точный лимит ещё не согласован.

## Критерии готовности текущего этапа

- Импортируемый Dify DSL хранится в проекте без секретов.
