# SpaceX Food — инструкции для работы

Актуализировано 2026-09-12. Этот файл — основной контекст для агентов. `agent.md` оставлен как ссылка сюда. Старые разделы отчётов в `docs/` описывают историю, а не обязательно текущие ограничения.

## Продукт и приоритет

B2B CRM для сербских кафан и ресторанов, созданная на SpaceX Hackathon Belgrade. Ресторан загружает фотографии бумажного меню, получает категории и блюда, обогащает карточки, принимает результат и публикует цифровое меню по QR. Сейчас приоритет — запись демо и стабильный сценарий на Render.

Пользователь общается на русском; интерфейс и генерируемый контент карточек — на английском. Оригинальные названия и исходные данные меню сохраняются. Не добавлять биллинг, сложные роли и новые сервисы без задачи.

## Архитектура

- `frontend/`: React 19, TypeScript, Vite 8, Tailwind 4, shadcn/Radix, Recharts.
- `frontend/convex/`: Convex Auth, организации, файлы, меню, продукты, категории, карточки, фоновые задачи и публичные снимки меню.
- `dsl/menu/`: Dify workflow распознавания фотографий меню; последняя исходная версия `0.0.3.yml`.
- `dsl/product/`: Dify workflow обогащения одного блюда; последняя исходная версия `0.0.8.yml`.
- Dify управляет LLM workflow; Grok используется для текста, Exa для фактов, fal.ai / Grok Imagine для изображений. Не переносить этот workflow в собственный сервер без задачи.
- `daytona/` и Convex `menuPdf*`: генерация A4 PDF и PNG-превью, преобразование входного PDF в страницы для Dify.
- Render раздаёт статический фронтенд; Convex деплоится отдельно.

## Реализованный сценарий

1. Страница входа с авторизацией. Заявка на ресторан пока заменена английским текстом об обращении к администратору; публичной формы регистрации на первом экране нет.
2. Настройки организации: название, контекст и фото стола. Фото стола используется в генерации и как обложка гостевого меню.
3. Импорт фото меню, состояния фоновых задач, категории и продукты в базе.
4. Редактор блюда: Generate/Regenerate, опциональное реальное фото, описание, подтверждаемые свойства и применение AI-черновика.
5. **Generate all cards** ставит блюда меню в очередь с задержкой; пропускает уже генерируемые и имеющие картинку. Закрытие браузера не отменяет очередь.
6. В публикации **Approve all generated cards** применяет готовые карточки; активные и ошибочные результаты не должны блокировать принятие остальных. Генерация сама не публикует меню.
7. **Publish / QR** проверяет готовность, сохраняет публичный снимок и возвращает ссылку `/menu/:slug` и QR. Гость открывает меню без входа.
8. **PDF / Print** рядом с меню: превью всех страниц, Download PDF, Print, Open PDF, ручная генерация/повтор, состояния и предупреждение об устаревшей версии. При ограничениях встроенного PDF-просмотрщика — Open PDF и печать браузером.

PDF автоматически пересобирается после импорта, изменений меню/продуктов, принятия карточек и публикации. Печатает сохранённые данные; QR добавляется для опубликованного меню при заданном `PUBLIC_APP_URL`. Старый PDF сохраняется при ошибке. Наличие реализации не означает успешный живой запуск Daytona: проверяйте статус задачи.

## Инварианты данных и изображений

- Все приватные операции проверяют принадлежность организации на сервере. Публичная витрина возвращает только предназначенные гостю данные.
- `catalog.applyCard` применяет английское имя/описание и сохраняет originalName. AI не должен автоматически менять цену, подтверждённые ингредиенты или аллергены.
- Публикация требует принятия актуальной карточки и отсутствия активной генерации. Правки черновика не заменяют опубликованный снимок без повторной публикации.
- Изображения fal сохраняются в Convex Storage, временный URL провайдера не является постоянным адресом карточки. Сохранять проверки HTTPS, домена, MIME и размера.
- Карточка: центрированная полностью видимая тарелка, примерно 50–60% ширины, стол как визуальный референс, английский заголовок и только разрешённые подписи/иконки.
- Фото реального блюда опционально: при наличии сохранять внешний вид блюда, переносить его на заданный стол. Без фото — иллюстративная подача.
- В product 0.0.8 картинка `card-reference` не передаётся модели: её рекламный текст ранее попадал в результат. Стиль задаётся текстом; legacy `card_reference_url` игнорируется.
- Не выдумывать подтверждение состава, калорий, vegan/spicy/детского меню и аллергенов. Неподтверждённые сведения остаются предположениями для проверки.
- Ошибка картинки не должна терять успешно сгенерированный текст. Полная история ответа хранится в карточке.

## Среды и секреты

- Репозиторий: `git@github.com:pavlov-victor/spacex-food.git`, рабочая ветка `main`.
- Фронтенд: `https://spacex-food-crm.onrender.com`.
- Используемый Convex dev: `https://good-aardvark-691.eu-west-1.convex.cloud`. Не переключать фронт на пустой production deployment без отдельной задачи.
- Render: `VITE_CONVEX_URL`, `NODE_VERSION=24.12.0`; build `npm ci && npm run build`, каталог `frontend`, результат `dist`, SPA rewrite из `render.yaml`.
- Convex: `DIFY_API_URL`, `DIFY_MENU_API`, `DIFY_PERSON_API` (ключ приложения product), `DAYTONA_API_KEY`, опциональный `DAYTONA_SNAPSHOT`, `PUBLIC_APP_URL` для QR в PDF.
- Dify: ключи fal/Exa в environment workflow; ключ провайдера Grok настраивается отдельно.
- Локальный `.env` автоматически не передаётся в Render, Convex или Dify. Не выводить ключи, значения Authorization и полный секретный MCP URL в логи, чат, git или клиентский bundle.
- `/tmp/`, `.env*` и `dsl/**/*-release.yml` игнорируются. Release DSL содержит секреты и предназначен только для ручного импорта.

## Dify и версии

Хранить независимые версии menu/product до первого релиза, не переписывать старые snapshots. Исходные YAML — без секретов. Сборка импорта: `python3 scripts/dsl_release.py dsl/product/0.0.8.yml`; создаётся соседний `0.0.8-release.yml` с объявленными переменными из `.env` и правами 0600.

Имеющийся MCP endpoint предоставляет запуск workflow, а не управление DSL. App API key также не даёт прав импорта/экспорта графа. Пользователь импортирует и публикует release в Dify; локальное изменение YAML не обновляет облако. Проверять фактическую workflow_version в результате API.

Сквозной Dify product 0.0.8 → fal → Convex Storage → Apply → Publish уже проходил. Созданные для проверки меню позднее удалены; старые demo slug и fixtures не считать действующими.

## Работа с кодом и git

- Перед изменением `frontend/` читать `frontend/AGENTS.md` и `docs/team-development.md`; для Convex — `frontend/convex/_generated/ai/guidelines.md`.
- UI и дизайн ведёт тиммейт; доступ к данным, hooks, backend и интеграции отделены от JSX. Пользователь также поручает этой сессии конкретные UI-доработки — выполнять их с сохранением дизайна и через hooks.
- В репозитории бывают одновременные изменения: сначала `git status`, перед push получить актуальный origin; сохранять работу тиммейта, разрешать конфликты осмысленно. Не делать force push, не включать чужие файлы через безусловный `git add .`.
- Пользователь просит **всегда пушить завершённые изменения**: после подходящих проверок commit/push без повторного запроса. Он проверяет Render. Успешный push не означает завершённый Render deploy.
- Генерируемые Convex API/types обновлять штатными инструментами. Локальный административный `convex/resetDemo.ts` не отслеживается: не включать его и ссылки на него в коммит случайно после codegen.
- Очистка демоданных — только по явной просьбе. Последняя операция удаляла меню, продукты, карточки, категории, связанные файлы/задачи и публикации аккаунта демо, сохраняя ресторан, фото стола и авторизацию. Не запускать reset или создающие данные smoke-тесты перед записью видео без задачи. Состояние базы после очистки может сразу измениться действиями пользователя.

## Проверки

В `frontend/`:

```sh
npm run build
npm run typecheck:backend
npm run test:backend
```

Запускать проверки по изменению: сборка для UI, typecheck/tests для backend. `npx convex dev --once` публикует функции в настроенный dev и обновляет типы; frontend push этого не делает.

Для DSL/PDF:

```sh
python3 scripts/dsl_lint.py --strict dsl/menu/0.0.3.yml dsl/product/0.0.8.yml
python3 scripts/test_dsl_lint.py
python3 dsl/product/test_workflow.py
python3 dsl/product/test_fal_workflow.py
python3 -m unittest discover -s daytona -p 'test_*.py'
```

Python-зависимости — `dsl/product/requirements-dev.txt` и `daytona/requirements.txt`. После изменения worker синхронизировать `python3 daytona/sync-worker.py`.

Браузерные тесты — Playwright в `frontend/`. Часть тестов зависит от прежних удалённых demo-организаций: проверять fixtures перед запуском. `frontend/scripts/smoke-demo-flow.mjs` создаёт данные и запускает платную генерацию; не использовать как безвредную проверку сборки.
